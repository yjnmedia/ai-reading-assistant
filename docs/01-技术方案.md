# 技术方案：可接入阅读器的 AI 检索与 AI 生图

> 本文描述一套**与客户端无关**的服务：任何阅读器只要加三个很薄的调用点，就能得到「边读边问」与「边读边看」。
> 演示客户端基于开源阅读器改造，只用于验证，不在本文与仓库内分发。

---

## 1. 要解决的问题

### 1.1 三个读者痛点

1. **看不懂**：官场、军事、年代文的人情与体制语境，读者要反复回翻；
2. **记不住**：几百万字后，某人物/物件首次出现在哪、上次提到是什么时候，读者查不动；
3. **不敢查**：手机上搜一下很容易搜到后文剧透。

### 1.2 为什么不能「把书塞进模型」

《重生之官道2026》实测 11,436,176 字节 / **3,974,713 字符**，折算约 **2.9M token**：

- 256k 上下文窗口的 **11 倍**；
- 换 1M 窗口也不够一本千万字的书；
- 每次问答都重发全书，成本与延迟都不可接受。

**所以：离线建索引（一次性），在线只取「读者当前位置之前」的一小段材料（每次）。**

## 2. 方案结构

三层，全部与客户端解耦：

```
阅读器（手机 App / 小程序 / 网页 / 桌面）
        │  ①当前位置前 200 字 + 问题（或：选中的一段 + 生图请求）
        ▼
云服务器（只做密文转发，不解密、不存书）
        │  ②mTLS 双向证书（服务端证书固定在客户端，客户端证书固定在服务端）
        ▼
家里 / 机房的一台普通 PC（24 小时开机）
        ├─ 本地索引库：章摘要 + 实体时间线（SQLite，60 MB 级）
        ├─ 检索：先唯一定位读者位置 → 只取该位置之前的材料
        ├─ 调大模型生成解释（不把整本书发给模型）
        └─ 生图：写词调模型，画图在本机显卡上跑
```

部署要点：

- **索引与画图都在自己机器上**：8 核 / 16G 即可；有显卡则生图也在这里。
- **云端零信任**：云只做 TCP 转发，TLS 在家里终止，云端看不到正文，也不存书。
- **失败即静默**：上报与查询失败不弹窗、不阻塞翻页，断网时阅读完全不受影响。

## 3. 对接契约：阅读器侧只有三处

### 3.1 问：选中文字 → 三档解释

请求（示意）：

```json
{
  "q": "接风宴上，自然都是空话套话，大家都互相审视着对方。",
  "anchor": "……黄向东年近五十，在黄海组织部门干了二十多年",
  "kind": "explain | why | tie"
}
```

- `anchor` 是**读者当前位置前 200 字原文**，用于在索引里唯一定位，不依赖章号；
- `kind` 决定给什么：`explain` 解释这段、`why` 为什么、`tie` 前文线索；
- 返回一段纯文本；`tie` 额外返回可点击的「章号 + 原句」。

### 3.2 图：段末 → 段评配图

请求：`{"text": 该段原文, "role": "可选角色名", "width": 960, "height": 1280}`
返回：**任务号**（立刻返回，不等画完）；之后阅读器轮询或收推送拿状态。

### 3.3 认书：进书 → 是否已有索引

请求：`{"title", "author", "head": 文件前 64KB}`
返回：`{"indexed": true, "similarity": 0.9956, "bookId": "..."}`

**阅读器不需要改正文结构、不需要上传整本书、不需要把用户数据交出去。**

## 4. 三项核心能力（AI 检索）

### 4.1 防剧透的定位（整个方案的地基）

**问题**：不能靠「第几章」定位。同一本书的连载版/精校版/合并版章号会错位——实测某版本按章号 1441 去另一版本取材料，只到对方第 748 章，**越界 693 章 = 全书 92.2%**。

**做法**：

1. 客户端只上报「当前位置前 200 字」；
2. 服务端在索引里做唯一定位，得到**内部章号**；
3. 检索时 SQL 硬条件 `ch_global < 当前章` 截断；
4. 提示词里的「不要剧透」只是第三道保险，不是防线。

模型拿到的材料物理上就不含后文，问后文才有的名字，只能回答「前文没有提到」。

### 4.2 跨设备认同一本书

- 书名 + 作者规范化建候选桶；
- 桶内用 **MinHash/KMV（4096 个最小 9-gram 哈希）** 比对；
- 阈值：≥0.90 同书、0.60~0.90 待确认、<0.60 不同书。

实测：同书异版 **0.9956**，两本毫不相干的书 **0.0000**（连字符数相同的截断异书也是 0）。

### 4.3 三档解释：按需要给，不一次性倒

| 档位 | 给什么 | 何时用 |
|---|---|---|
| 解释这段 | 这段在讲什么、人物关系，200~300 字，最多 3 条 | 默认 |
| 为什么 | 一句因果 + 来龙去脉 + 依据（本段／本章前面） | 读者问「为什么会这样」 |
| 前文线索 | 这段里的人/物，前文首次出现与最近提及，可点回原章 | 读者想不起这人是谁 |

四条设计原则（踩坑之后定的）：

- **默认少给**：最多 3 条、350 字内；通用官职与常见机构不解释。
- **不替任何一方辩护**：原文写到违规、腐败、权色交易，就如实说性质与后果，不加「个别现象」这类平衡话，也不反向嘲讽。
- **「为什么」必须给整章**：实测只给上一章末 1000 字，答案材料不足率 **5→5 完全没降**；给整章才降到 0。
- **不做读者画像问卷**：唯一直接对照实验（PLAI, MuC 2026）显示画像组与无画像组知识测验无显著差异；正确做法是条数预算 + 白名单过滤，再做「这本我熟」开关。

### 4.4 两家模型共用一份提示词

同一段写回扣、串供、陪酒的情节，两家模型的「敢说程度」不同：豆包会往概念解释靠（把受贿说成「商业贿赂」），DeepSeek 直说罪名与当年普遍程度。工程上两条约束：

- 提示词是一份常量，**改一边必须同时改另一边**；
- 模型可切，默认选直说那个。

## 5. AI 生图链路

### 5.1 阅读器为什么需要生图

三段式价值，从低到高：

1. **段评配图**：读者看到「那一场」，图挂在具体段落上，能被回看——这是留存价值；
2. **角色一致**：同一角色多版定妆 + 出场画面归属，人物不换脸——这是可信度；
3. **一句话创作**：读者自己写一句画面描述就能出图，或拿一张图反推提示词——这是参与感。

孤立的图库没人回访，**图必须挂在「段」和「角色」上**。

### 5.2 两条链路的区别

| | 段评配图 | 自由创作 |
|---|---|---|
| 输入 | 书里选中的那段原文 | 用户一句画面描述，或一张图反推 |
| 角色一致性 | 带角色卡（定妆多版本） | 不带参考，每次独立 |
| 去处 | 挂到该段，可「前往」跳回原段 | 进图库，可存相册 |
| 归属 | 归属到具体角色，可改、可单张删 | 无 |

### 5.3 提示词工程（五段式落地）

主体 → 服饰 → 姿态 → 环境光线，四段写完后把**敏感部位写进第三段**（避免污染着装描述）。写词模型只负责「说清楚」，不负责画。

内容策略在服务端用关键字控制（如 `nsfw`、`nsfw 露胸`），客户端只透传一句修改意见、不过滤；涉未成年一律拦截。

### 5.4 任务模型：提交即返回、可连提多张

- 提交立刻拿任务号，界面转圈 1 秒后变成「已提交，正在画…·已等 N 秒」；
- 底部显示「正在生成（1/3）→（2/3）→（3/3）」；
- 未完成的格子显示占位块 + 秒表，失败显示红块 + 原因 + 删除；
- 同段重复提交会被拒，并提示「这张已经画完了；想重画请写一句修改意见」。

### 5.5 尺寸与画质分档

- 短边 480p / 720p / 1080p / 1440p / 4K（2160p），长边按画幅换算并对齐 16 的倍数；
- 步数 30（快速）/ 40（标准）/ 50（质量）；
- 默认 720×1280 + 标准，约 43 秒。

### 5.6 为什么画图放在自己机器上

1. 显卡与权重不出门，成品图不回传第三方；
2. 不用养常驻 GPU 实例，一张一张按需排队，闲置零成本；
3. 与检索共用一条 mTLS 通道，客户端只多一个「提交任务」，不新增网络面与证书；
4. 画质档位、尺寸上限、内容策略都能在自己这侧定。

代价：一张图 40 秒到几分钟，所以才有上面的「提交即返回」。

## 6. 实测数据

### 6.1 索引成本（889 章去重后）

| 项 | 数值 |
|---|---|
| 章摘要 | 889 条，每条 150~200 字 |
| 上层聚合 | 89 条（每 10 章一条），250~350 字 |
| 调用次数 | 978 次 |
| token | 输入 2,887,242 / 输出 148,218 |
| 费用（批量价） | **约 5.44 元/本** |
| 耗时 | 5 并发约 25~30 分钟 |

反例：把「5 章合一」能省 **4.7%** 的钱，但问答正确率 8/8→3/8、章号定位 8/8→2/8，**故不做粗粒度合并**。

### 6.2 在线问答

- 单次约 **0.011 元**（解释这段）~ **0.03 元**（前文线索）；
- 关掉「深度思考」后从 51.4 秒降到 **5.5 秒**；
- 通道：带客户端证书 `GET /api/ask` → `ok=true`、**127 ms**、817 字。

### 6.3 生图

| 尺寸/画质 | 耗时 |
|---|---|
| 720×1280 / 标准 40 步 | 约 43 秒 |
| 720×1280 / 快速 30 步 | 约 34 秒 |
| 720×1280 / 质量 50 步 | 约 55 秒 |
| 4K | 分钟级 |

连提三张不阻塞，进度（k/n）逐张推进；图库现状 274 个角色、上千张图，全在本机。

### 6.4 稳定性

- 服务进程被杀，看门狗 **45~70 秒**自动拉起（多次实测）；
- 断网切章只记一行 `report failed`，界面无弹窗；联网自动恢复；
- 云端持证访问 `/health` 200，不带证书握手直接失败（mTLS 生效）。

## 7. 落地建议

### 7.1 给已有阅读器的三种接法

| 方式 | 说明 | 适合 |
|---|---|---|
| **外挂服务**（最快） | 阅读器只加三个调用点，索引与画图留在自己机器 | 想先验证效果、不想动主工程 |
| **私有化** | 索引与画图进程部署到自己机房，去掉云转发这一层 | 有合规要求的平台 |
| **只取提示词与索引管线** | 用本文的四条原则与五段式规则，接自家模型 | 已有 AI 中台、只缺方法 |

### 7.2 给自研阅读器的最小路径

1. 先把「当前位置前 200 字」这个锚点做进阅读内核（这是唯一必须改客户端的地方）；
2. 建一份章摘要索引（哪怕只做 100 章验证）；
3. 检索时 SQL 硬截断在当前章之前；
4. 三档解释先做「解释这段」，跑通再补「为什么」与「前文线索」；
5. 生图最后做，因为它需要显卡和排队机制。

## 8. 接入要付多少成本

分三笔账：**改客户端的人力**、**机器与带宽**、**按量花的模型钱**。前两笔是固定投入，第三笔随规模线性增长——所以下面单列一页算给你看。

### 8.1 客户端改造：3~4 人日

| 改动项 | 工作量 | 说明 |
|---|---|---|
| 位置 → 「前 200 字」锚点 | 1~2 人日 | **唯一必须进阅读内核的改动**：从当前页首字往前取 200 字；翻页/滚动中要取稳定值 |
| 选中菜单加两项 | 0.5 人日 | 「解释这段」「前文线索」 |
| 段落「配图」入口 + 图位 | 1 人日 | 段末小按钮 + 一张缩略图位 + 点击查看 |
| 进书时报书名作者与文件头 | 0.5 人日 | 只上传书名、作者、文件前 64KB |

**合计 3~4 人日**（含与我们对接口的联调）。不涉及正文结构调整、不涉及数据库迁移。

### 8.2 服务端：外挂几乎为零，私有化 2~3 人日

| 接法 | 你们要做的 | 人力 |
|---|---|---|
| **外挂服务** | 加一条出网白名单 + 固定我们的证书 | ≈0（半天配置） |
| **私有化** | 部署索引服务与生图服务，去掉云转发层 | 2~3 人日 |
| **只取提示词与索引管线** | 把四条原则与五段式规则接进你们自己的模型中台 | 3~5 人日 + 你们模型调优 |

### 8.3 机器与带宽

| 项 | 规格 | 费用 |
|---|---|---|
| 索引机 | 8 核 / 16G，60MB 级 SQLite | 既有 PC 为 0；云主机约 **300~600 元/月** |
| 生图机 | 单张 4090 级别显卡 | 自备约 1.3 万元一次性；云上按需约 2~3 元/小时 |
| 公网带宽 | 只传「前 200 字 + 问题」，单次几十 KB | 实测 6 Mbps 出口即可跑检索；生图**不下行图片**，只传任务状态 |

**带宽不是瓶颈**：整本书不上传，检索通道 127ms。只有生图结果需要下发，而那是几百 KB 一张、可懒加载。

### 8.4 模型 API：按量，随规模线性

| 项 | 单价（实测） |
|---|---|
| 建索引（一次性） | **5.44 元/本**（889 章，978 次调用，25~30 分钟） |
| 解释这段 | **0.011 元/次** |
| 前文线索 | **0.03 元/次** |

规模化后的索引账单（只算「被问到过的书」）：

| 书量 | 一次性索引费 | 建库总耗时（5 并发） |
|---|---|---|
| 1,000 本 | 约 5,440 元 | 约 21 天 |
| 10,000 本 | 约 5.44 万元 | 约 208 天 |
| 100,000 本 | 约 54.4 万元 | 约 5.7 年 |

**所以不要全站预建索引**——见 8.7 的懒建策略，实际只给「第一次有人提问的书」建。

在线问答按次算：10 万次/天 ≈ 1,100~3,000 元/天；100 万次/天 ≈ 1.1~3 万元/天。

### 8.5 生图成本

| 方式 | 单张成本 | 备注 |
|---|---|---|
| 本机 4090 | **约 0.01 元**（纯电费） | 43 秒/张，单卡满负荷约 83 张/小时 |
| 云上生图 API | 0.1~0.3 元/张 | 省机器钱，但单价高 10~30 倍、且要过内容审核 |

**结论**：日均出图超过约 300 张，本机显卡就比云 API 便宜，且图不回传第三方。

### 8.6 三种规模的总账

| 场景 | 固定投入 | 变动成本 | 谁适合 |
|---|---|---|---|
| **个人作者 / 自研阅读器** | 1 台自己的 PC（0 元）+ 3~4 人日 | 索引 5.44 元/本，问答几分钱一次 | 想先跑通效果 |
| **中小平台试水** | 1 台云索引机 + 1 张显卡，约 300~600 元/月 | 索引 5.44 元/本（只建热门书），问答按次 | 想验证留存 |
| **全站铺开** | 索引集群 + GPU 池，按 QPS 定 | 索引费按「被问到的书」计，问答按 DAU 计 | 已有 AI 中台，只接能力 |

### 8.7 省钱杠杆（按效果排序）

1. **懒建索引**：第一次有人提问才建这一本。全站 100 万本，实际可能只有几万本被问过。
2. **索引共享**：同一本书只建一次，多用户共用（MinHash 认书就是为这个）。
3. **条数预算**：默认 3 条、350 字内。实测比换模型省得多，且体验更好。
4. **摘要缓存**：同一章只摘要一次，重试不重复付费。
5. **生图降档**：默认 720p + 标准（43 秒）；4K 只在「存相册」时给。
6. **关深度思考**：单次延迟 51.4 秒 → 5.5 秒，且 token 更少。

## 9. 交付边界

**可交付**

- 索引构建管线：分章、摘要、聚合、实体时间线、SQLite 结构；
- 检索与问答服务：位置定位、前文截断、三档解释的提示词与参数；
- 生图链路：五段式提示词与写词规则、任务排队与状态、图库与角色卡的数据结构；
- 通道设计：云转发 + 家里 mTLS 的部署方式与运维脚本说明；
- 成本模型与验收指标。

**不包含**

- 阅读器客户端程序与安装包（演示壳基于开源阅读器改造，不对外分发）；
- 模型权重；
- 任何第三方库源码。

---

## 10. 后续可加（按性价比排序）

1. **条数预算 + 白名单过滤**：直接解决「解释过多」；
2. **「这本我熟」开关 + 逐词「不用解释」记忆**；
3. **问书支持多轮追问**（当前单轮）；
4. **生图按书分目录、段评图按书过滤、自动裁白边**；
5. **同段多版对比 + 把提示词带进创作页**。
